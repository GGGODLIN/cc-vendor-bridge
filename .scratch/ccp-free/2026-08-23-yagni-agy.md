## 三句入口
- 這輪在審值不值得做：審查是否需要為了接入 NVIDIA NIM 免費模型而引入獨立 Free Claude Code 服務、launchd 守護進程與專屬 `ccp-free` wrapper。
- 太早的部分：過早規劃未來多 provider 擴展架構（US13）、專屬健康狀態文檔紀錄機制（US14）、動態模型探索（ID9）以及繁複的 7 天 trial 流程與 Docker 驗證。
- 現在只需決定：是否同意將範圍收斂至「獨立 venv 安裝鎖定版本 FCC + 注入現有 NVIDIA NIM key + 綁定 localhost 獨立 port + 建立 `ccp-free` wrapper + 一次性真實 prompt 驗證」。

---

## 一頁最簡方案
1. **獨立環境安裝**：在專屬目錄下建立 Python venv，安裝鎖定 commit 的 Free Claude Code 核心依賴，不執行 upstream 的全套安裝腳本。
2. **最小隔離配置**：
   - 建立獨立 runtime 目錄（如 `~/.fcc-free`），綁定 `127.0.0.1` 與專屬 port。
   - 僅讀取現有 CLIProxyAPI 設定中的 NVIDIA NIM key 寫入該設定，不配置其他 provider，也不設定付費 fallback。
3. **服務與 Wrapper**：
   - 建立最小 launchd service（或背景守護設定）以維持與既有 `ccp-relay` 一致的生命週期管理。
   - 建立 `ccp-free` wrapper，在啟動 Claude Code 前進行 port 健康檢查，並以 process-local 環境變數注入 endpoint 與 token，指向固定的 NVIDIA 模型。
4. **一次性真實可用性驗證**：
   - 以 curl 對本機端點發送真實 prompt 請求，確認 NVIDIA NIM 能成功回應非空文字。
5. **最小復原支援**：
   - 提供一份單純的清理指令/腳本（停止服務並刪除該 venv 與 runtime 目錄），不額外引入 Stage 0 Docker 或多層狀態追蹤。

## 最終建議
`縮成最簡版`
理由：核心需求（獨立 `ccp-free` + 隔離 FCC + 單一 NVIDIA NIM 驗證）方向正確且能滿足免費端點目標，但應剔除動態模型探索、狀態文檔機制與過度繁重的試驗流程，專注於最小可運行的隔離驗證路徑。
